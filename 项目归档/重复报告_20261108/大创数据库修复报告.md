## 二、逐项修复说明

### P0-1 · 药材-成分归属重建

**问题**：`rel_herb_compound` 1,657 条关联中，1,588 条可比对的记录里只有 12 条（0.8%）能在溯源 Excel 中找到依据。抽查确认是随机抽样填充，而非 ID 错位（每味药与源表所有药材逐一比对，最佳匹配平均只命中 1.37 个成分）。

**修复**：以 `数据库溯源/主要展示数据均为cctcm2.0/药材-化合物-含量-赵玉男.xlsx` 为唯一真源重建。

- 名称匹配三级策略：精确 → 去括号别名 → NFKC 归一化
- 覆盖 264/278 味药材（14 味在源表无成分记录：阿胶、柏子仁、蝉蜕、大戟、谷芽、鸡内金、荔枝核、南沙参、胖大海、桑螵蛸、薏苡仁、玉竹、紫河车、龙骨）
- 源表 2,444 个成分中，1,405 个在库内 569 个成分中不存在（库是源表的子集）
- 旧表保留为 `rel_herb_compound_old`

**验证**：薄荷 → 17 个成分（刺槐素、β-香叶烯、香芹酮等）；人参 → 13 个成分全部为人参皂苷类；甘草 → 10 个成分含甘草酸、甘草苷、异甘草素。

> ⚠️ **发现源数据本身的问题**：导师提供的源表中，甘草被错误地关联了白芍苷、芍药苷、苯甲酰芍药苷（这三个是白芍/赤芍/牡丹皮的成分）。这是源表录入错误，本报告如实记录，未擅自修改导师原始数据。

### P0-2 · 成分理化属性重算

**问题**：`compound.mw` 与 SMILES 计算值 **0/569 一致**；`logp` 与 RDKit Crippen 计算值仅 54/569 接近。KS 检验显示 mw 符合 U(150,500)、logp 符合 U(-1,5) 的均匀分布（真实数据 D=18.7 被彻底拒绝），确认是随机数。

**修复**：

- `mw`：RDKit `Descriptors.MolWt` 从 SMILES 重算，569/569 全部成功
- `logp`：优先取 `化合物理化性质和生物利用度属性-赵玉男.xlsx` 的实测 LogP（552 条），其余用 RDKit `Crippen.MolLogP`（17 条）
- `smile_short`：改为 RDKit 规范 SMILES 的截断摘要（≤60 字符），前端列表页展示正常
- 顺带修复 3 个损坏的 SMILES（葵烷、人参皂苷Rd、十六烷酸），从 `化合物数据_cctcm2.0.xlsx` 回填正确值
- `target_count`：33 条与实际关联数不符，已全部对齐

**验证**：569 条 mw 与 RDKit 计算值误差均 < 0.02。

### P0-4 · 靶点关联脏字段清空

**问题**：

- `source_db`：同一篇文献 PMID 32699268 的 3,698 行被平均分到 5 个库（各 732–754 条）；整体 5 库各占约 20%，真实多源整合不可能如此
- `network_centrality`：40,634 条全部非空，取值 0.0–1.0，每 0.1 桶约 4,000 条，`random.uniform(0,1)` 的典型特征

**修复**：两列全部置 NULL。前端已有 `or "—"` 兜底，不会报错。

> 注：关联本身（compound_id + target_gene）**是真实的**——40,634 行与 `化合物作用靶点.xlsx` 逐行 100% 一一对应。只有这两个附加标签是编的。

### P1-1 · 方剂组成重建

**问题**：274 条记录中 28 条把多味药合并成一个字符串（如 `黄芪/干姜`）。经分析，这张表是**两批数据拼接**而成：

| 批次 | 记录数 | herb_id 格式 | 合并串记录 |
|---|---|---|---|
| 旧批（id 1–97） | 97 | 纯数字 | **28 条全在这里** |
| 新批（id 98–274） | 177 | `ccTCM` / `imp:` | 0 条 |

在 `herb_name == Herb.name` 精确 JOIN 中会丢失 29 条（10.6%），直接影响方剂雷达图、网络图和入血成分统计。

**关于合并串的性质**：这 28 条记录的 `dosage` **全部为空**，而 246 条单味记录**全部有剂量**。它们来自导师复方表里「某成分同时归属多味药」的写法（如 `白芍/甘草` 表示 albiflorin 同时存在于白芍和甘草），属于成分归属信息，不应混入方剂组成表。

**修复**：以导师源表 `中药复方血中移行成分数据集.xlsx` 的「药材组成」列为准重建。

- 逐首核对 46 首方剂，组成与源表 100% 一致
- 生成 246 条关联，全部能 JOIN 到 herb 和 prescription
- 剂量直接采用源表括号内的克数
- 后端 JOIN 从 `herb_name == Herb.name` 改为 `herb_id == Herb.id`（3 处）
- 补录数据库中缺失的药材「灵芝」（`imp:灵芝`，源表生脉方用到）

**修正的组成错误**（原库与源表不符）：

| 方剂 | 原库 | 源表（已按此修正） |
|---|---|---|
| 麻黄桂枝汤 | 4 味（含杏仁、甘草） | **2 味**（麻黄、桂枝） |
| 柴胡桂枝汤 | 人参 | **党参** |
| 生脉散 | 人参 | **红参** |
| 生脉饮 | 人参 | **党参** |
| 生脉方 | 3 味 | **8 味**（+黄芪、地黄、灵芝、山慈菇、佛手） |
| 黄芪桂枝五物汤 | 生姜 | **干姜** |

旧表保留为 `rel_prescription_herb_old`。

### 三维机制评分 · 真实 GSEA 重算

**问题**：`radar_*` 三列经检验为随机数——按 40-100 的 61 个整数桶做卡方检验，χ²=61.91/55.04/59.33（df=60，5% 临界值 79.1），全部落在均匀分布内；三列两两相关系数 −0.05/−0.02/−0.07，完全独立；全为整数，最小值都恰好是 40.0。项目内（含 git 全部历史）无任何生成代码，溯源目录无对应文件。

**修复**：用真实 Enrichr 富集分析重算，写入新列 `radar_*_gsea`，原列保留供对照。

**技术要点**：

1. **绕开损坏的 gseapy**：本项目 `gseapy 0.10.8` 在 `enrichr.py:427` 使用了 pandas 2.x 已移除的 `DataFrame.append()`，导致 `pharmacology.py` 的 GSEA 降级路径**完全不可用**（异常被捕获后返回硬编码的 45/52/38）。改为直接调用 Enrichr REST API。
2. **评分公式改进**：初版直接累加 overlap 并线性缩放，导致 50% 成分撞到 98 分上限。诊断发现各维度 overlap 与「命中通路总数」相关系数高达 0.89~0.93——靶点多的成分三个维度同步升高，三个维度退化成同一个信号。
3. **最终公式**：`维度得分 = (该维度 overlap / 总 overlap) × log(1 + 总 overlap)`
   - 占比刻画「作用偏向哪个维度」
   - log 强度刻画「整体证据量」
   - 最后对全体做分位数归一化到 0-100
4. **不做假兜底**：无富集命中就是 0 分（109 个成分抗炎为 0），不再返回伪随机基线

**结果**：

| 指标 | 旧值（随机） | 新值（GSEA） |
|---|---|---|
| 有值成分 | 569 | 415（154 个靶点不足 2 个，无法富集） |
| 抗炎 均值/标准差 | 69.1 / 17.2 | 37.0 / 33.1 |
| 免疫 均值/标准差 | 70.9 / 17.4 | 34.6 / 33.3 |
| 气道 均值/标准差 | 70.3 / 17.2 | 38.1 / 32.5 |
| 抗炎×免疫 相关 | −0.05 | 0.68 |
| 抗炎×气道 相关 | −0.02 | 0.35 |
| 免疫×气道 相关 | −0.07 | 0.28 |
| 满分饱和 | 无（40-100 均匀） | 各维度仅 2 个 100 分 |

新分布标准差从 17 升到 33，有真实零值，相关性降到合理区间，区分度显著提升。

**样例**：姜黄素（抗炎 83 / 免疫 83 / 气道 40）、麻黄汤（抗炎 64 / 免疫 68 / 气道 69）。

## 五、遗留事项

1. **GSEA 覆盖 415/569**：154 个成分因人类蛋白靶点不足 2 个无法做富集分析，其 `radar_*_gsea` 为 NULL，接口会回退到旧列值。若要彻底解决，需要补充这些成分的靶点数据。
2. **旧 `radar_*` 列未删除**：保留作为回退和对照。建议在论文/答辩中明确使用 `radar_*_gsea`。
3. **14 味药材无成分数据**：阿胶、柏子仁、蝉蜕等 14 味在源表中没有成分记录，其成分列表为空属正常。
4. **源表本身的甘草-白芍成分错误**：见 P0-1 的说明，需向导师确认。
5. **gseapy 兼容性问题未修**：`app/services/pharmacology.py` 的降级路径仍不可用。当前主路径已改为直接读 `radar_*_gsea`，但若将来需要动态计算，需升级 gseapy 或改用 REST API。
6. **`prob_cctcm` 溯源文件不一致**：`数据库溯源/入血概率cctcm2.0/cctcm_v2_predictions.csv` 是旧版预测结果，数据库实际使用的是 `入血预测/cctcm2.0_v2/cctcm_v2_predictions_union.csv`（V2 union 模型，git 提交 f2d4df3 重灌）。建议在溯源目录加说明，避免后人误判。
